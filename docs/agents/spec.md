# Spec body

A spec issue is the workstream's source of truth. Keep it short enough to read in one sitting and complete enough for an implementation session to work from.

## Sections

- **Context.** What is wrong or missing, with links to the code or the report.
- **Decisions.** The choices already made and why. Link the ADRs.
- **Work.** The layers or files, enough to split into tickets when the work is multi-session.
- **Docs.** For a developer-facing surface, list a tutorial and a reference. The tutorial goes from nothing to a working example and links to the reference. The reference links back. The tutorial uses the tested example. UI copy follows `CODING_STANDARDS.md`.
- **Tests.** Unit, integration, and the hardware or manual checks.
- **Acceptance.** Checkable outcomes.
- **Out of scope.** What this work does not do.

## Before publishing

- Read `docs/agents/issue-tracker.md`.
- Put the body in the issue, not a temporary file.
- Wait for the human before creating or editing the issue.
